# Contributing Guide

Everyone is graded individually, and the interviews ask each member to explain
the entire project. This guide exists to make that realistic.

## 1. Non-negotiable rules

1. **Write your own code.** The project guidelines state that the code must be
   written by the team and not generated by AI. Re-read the course AI policy
   before you start. Do not paste AI-generated code into the repo. Plagiarism
   means a zero for the project.
2. **No STL as a basis.** Do not include any of these headers in `include/`, `src/`
   or `benchmarks/`: `vector, list, forward_list, deque, map, unordered_map, set,
   unordered_set, stack, queue, priority_queue, array, bitset, algorithm, functional`.
   `make check-stl` enforces this.
   Allowed basics: `<cstddef> <cstdint> <cstring> <cstdlib> <cstdio> <cassert>
   <new> <utility> <chrono> <iostream> <fstream> <string>`.
   *Open question for the TA: are `<string>`, `<fstream>`, `<random>`, `<chrono>`
   fine? We plan to use our own xorshift RNG instead of `<random>`.*
   In `tests/` you may be allowed to use STL as a reference oracle. Confirm with the TA first.
3. **Understand every line you commit.** In the interview you must explain every
   line of your part and the design decisions behind it.
4. **Commit as yourself.** Your own name and your GitHub-linked email, so the
   history proves what you wrote.

## 2. One-time setup

```
git clone <repo-url>
cd <repo>
git config user.name  "Your Full Name"
git config user.email "your-github-email@example.com"
make test        # should run (and say there are no tests yet)
```

## 3. Branches and pull requests

- `main` always compiles and passes `make test`. Nobody pushes directly to `main`.
- Branch names: `feature/<yourname>-<component>`, e.g. `feature/ali-disk-store`.
- Commit small and often. Message style: imperative, specific.
  `Add HashTable resize at load factor 0.75`, not `update` or `fix stuff`.
- Open a pull request early (a draft is fine). The PR template lists what the
  reviewer checks.
- **Reviewer rotation** (each PR needs one approval before merge):

  | Author | Reviewer |
  |---|---|
  | Omar A | Ebrahim |
  | Ebrahim | Ali |
  | Ali | Youanes |
  | Youanes | Omar B |
  | Omar B | Omar A |

- Review for: correctness, memory safety, comment quality, and whether you could
  explain it in the interview. If you can't, ask the author until you can.
- Merge with a normal merge or squash. Do not rewrite shared history (`push --force` on shared branches).

## 4. Code style

| Thing | Convention |
|---|---|
| Files | `snake_case.h` / `snake_case.cpp` |
| Classes / structs | `PascalCase` |
| Functions / methods | `camelCase` |
| Data members | `trailing_underscore_` |
| Constants | `kPascalCase` |
| Header guards | `#pragma once` |

- Templates live in headers (`include/...`). Non-template code goes in `src/`.
- Data structures that own memory: write the destructor, and **delete the copy
  constructor and copy assignment** (`= delete`) unless you implement them
  properly. This avoids double-free bugs and keeps your explanation simple.
- Prefer raw `new`/`delete` with clear ownership comments. Every `new` needs a matching `delete` you can point to.

## 5. Documentation standard (graded)

The rubric requires comments explaining **purpose** of classes, functions and
variables, the **logic** of key operations, and **design decisions**.

Every file starts with a header block:

```cpp
// File:    doubly_linked_list.h
// Author:  <your name>
// Purpose: Doubly linked list with O(1) insert/remove at both ends and O(1)
//          removal of an arbitrary node given its pointer.
// Used by: LRUCache (recency order), LFUO1Cache (key lists inside frequency nodes)
```

Every class and every public function gets a comment with:

- what it does and what it assumes (preconditions),
- its time complexity,
- the invariant it maintains, where relevant,
- **why** you chose this design over an alternative (for example, sentinel nodes versus null checks).

Non-obvious lines get an inline comment. Obvious lines don't need one.

## 6. Testing

- One `tests/test_<component>.cpp` per component. Each builds to its own binary,
  has a `main`, and returns non-zero on failure (use `assert` or a small
  check function).
- `make test` builds with AddressSanitizer and UndefinedBehaviorSanitizer. A leak or out-of-bounds access fails the build.
- Test: empty structure, one element, many elements, duplicates, removal of the
  head/tail/only element, growth past capacity, and a randomised stress test.

## 7. Definition of done (for any component)

- [ ] Compiles with no warnings (`-Wall -Wextra -Wpedantic`)
- [ ] `make test` passes, including sanitizers
- [ ] `make check-stl` passes
- [ ] File header, class comments, function comments, complexity noted
- [ ] PR reviewed and approved by the assigned reviewer
- [ ] You can explain every line without looking at it
